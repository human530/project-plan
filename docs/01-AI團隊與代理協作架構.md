# AI 團隊與代理協作架構

> 一句話定位：把這個單人科展專題，當成一支「AI 團隊」來經營——由一位**總指揮（學生 + Claude 協調者）**帶領數個**專責 AI 子代理**平行作業，讓一個人也能擁有一支研究團隊的產出與紀律。

---

## 0. 為什麼要「AI 團隊化」

這是個人作業，但工作橫跨**資料、機器學習、統計評估、專案管理、醫學把關**五大領域。單線處理會卡關、會顧此失彼。把每個領域抽象成一個**專責代理（agent）角色**，可以：

- **平行推進**：彼此不相依的工作同時做（例如資料申請等待期間，先把模型骨幹與評估腳本準備好）。
- **責任清晰**：每個角色有明確輸入、輸出、完成定義（Definition of Done）。
- **降低遺漏**：醫學倫理、統計嚴謹這類最容易被高中生忽略的面向，各有專人盯。

這份藍圖有兩個層次：
1. **概念層（角色分工）**：規劃專案需要哪些「角色」，由學生扮演或由 Claude 子代理協助。
2. **執行層（實際代理）**：如何用 Claude Code 的平行子代理，把這些角色變成真的會自動產出的代理。

## 2. 各代理角色卡（Role Cards）

### 2.1 資料與法遵代理（Data & Compliance）
- **使命**：把「拿不到資料」這個最大風險降到最低，並建立乾淨、無洩漏、合倫理的資料管線。
- **輸入**：資料集需求、倫理規範、Colab/Drive 環境。
- **輸出**：資料申請與備援策略、前處理管線、patient-level 切分、去識別化檢核清單（→ 文件 02）。
- **完成定義**：MVP 可用資料就位、切分無病人跨集、倫理檢核通過。

### 2.2 模型與訓練代理（ML Architecture）
- **使命**：在小樣本 + 免費算力限制下，設計**會收斂、不過擬合、可重現**的模型。
- **輸入**：資料管線、任務定義（SvH 的序數性質）。
- **輸出**：分層模型架構、遷移學習策略、損失函數、Colab 訓練 SOP（→ 文件 03）。
- **完成定義**：MVP 模型端到端跑通、可 checkpoint 續訓、固定 seed 可重現。

### 2.3 評估與可解釋性代理（Evaluation & XAI）
- **使命**：用**對的指標**證明（或誠實否證）模型與專家一致，避免統計陷阱。
- **輸入**：模型預測、專家分數、實驗設計。
- **輸出**：指標清單（ICC/Bland–Altman/相關/RMSE）、實驗矩陣、Grad-CAM 量化方法、成功標準（→ 文件 04）。
- **完成定義**：一致性以 ICC + Bland–Altman 報告、含信賴區間、Grad-CAM 有量化證據。

### 2.4 專案管理與賽事法遵代理（PM & Competition Compliance）
- **使命**：守住 16 個月時程與範圍，確保 TISF 送件不漏件。
- **輸入**：四領域進度、TISF 規定、學生課業節奏。
- **輸出**：每月里程碑、風險登記表、研究日誌制度、送件檢核清單（→ 文件 05）。
- **完成定義**：每月有可交付里程碑、風險有應變、送件文件齊備。

### 2.5 醫學/領域把關代理（Domain Reviewer，人類為主）
- **使命**：確認臨床敘述、標註合理性，避免醫學錯誤與過度宣稱。
- **輸出**：臨床敘述審查意見、免責聲明把關、問答準備。
- **完成定義**：報告中所有醫學陳述經懂醫學/放射者確認。

## 3. 代理協作流程（依賴與平行）

```
階段 A：奠基（可大量平行）
  Data：啟動資料申請 ┐
  ML  ：環境建置/骨幹選型/序數頭實作 ├─ 互不相依，全部並行
  Eval：評估腳本/ICC/Bland-Altman 雛形 ┘
  PM  ：建研究日誌、Git/Drive 備援、里程碑表

階段 B：MVP（部分相依）
  Data 完成 → ML 訓練 MVP → Eval 量化一致性 → PM 記錄里程碑
                                  └→ Grad-CAM 可解釋性

階段 C：進階（相依鏈最長，需提前準備）
  Data(關節標註) → ML(關節定位+逐關節) → Eval(進階 vs 基線比較·消融)

階段 D：收斂送件
  全代理 → 報告/海報/中英文摘要 → Domain 把關 → PM 依 TISF 送件
```

**關鍵排程原則**：資料申請是**最長前置作業**，必須在階段 A 立即啟動；等待期間其餘代理全力平行，避免空轉。

## 4. 執行層：如何把「角色」變成真的平行子代理

本計畫即以此方式產出——由 Claude 總指揮**同時派出多個子代理**，各自深化一個領域並寫出文件。可重複使用的工作模式：

| 模式 | 適用情境 | 做法 |
|------|----------|------|
| **平行扇出（fan-out）** | 多個互不相依的調研/草稿 | 一次派多個子代理，各寫一份文件後彙整 |
| **接力（pipeline）** | 有前後依賴（資料→模型→評估） | 前一代理產出當作後一代理輸入 |
| **審查（review）** | 需要交叉把關 | 由把關代理檢視另一代理的產出 |
| **迭代優化** | 文件需多輪打磨 | 同一代理帶上回饋持續精修 |

**給學生的實作建議**：在 Claude Code（或 claude.ai）中，把每個角色卡當成一個子代理的任務指令，明確給定「背景、輸入、要交付什麼、完成定義」，就能複製這套團隊運作；不相依的任務務必同批派出以並行省時。

## 5. 治理規則（避免 AI 團隊失控）

1. **範圍守門**：任何「順手多做一點」的提議，先問是否屬本屆範圍（見文件 00 §2）；越界一律歸入未來展望。
2. **人類最終把關**：醫學陳述、倫理免責、最終送件由人類確認，AI 僅輔助。
3. **可追溯**：每個代理的產出進 Git，研究日誌記錄決策與理由（評審會問）。
4. **誠實優先**：所有引用數字標明來源、不確定處標註「需確認」，禁止編造文獻或結果。
5. **單一事實來源**：四份領域文件為各領域的權威來源，衝突時以文件 00 的範圍定義為準。
